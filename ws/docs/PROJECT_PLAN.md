# 项目计划

本页记录开发的现状、推进顺序、开发中遇到的理论缺口和已定的长期决定。目标、原则与架构设想见 [项目目标](PROJECT_GOALS.md)；实验平台（上游 G1 demo）的说明见 [平台设计](platform/G1_DESIGN.md) 与 [操作手册](platform/G1_MANUAL.md)。每一步执行前按当时情况复核。

## 现状

2026-10-31：

- **平台可用。** 三个容器（`dev`、`sim`、`policy`）就绪，上游 G1 闭环在本机可运行：8 个 episode 成功 3 个（95% 置信区间约 14%–69%），场景资产已缓存，启动约 40 秒，单个 episode 墙钟 2–3 分钟，两边同时运行时显存约 10 GB / 12 GB。数据见 [操作手册](platform/G1_MANUAL.md#本机实测)。
- **失败观察。** 2026-10-31 的 6 次中有 3 次掉落盒子，其中一次是放入时盒子在松手瞬间被弹出箱外，疑似仿真接触问题而非策略失误，尚未验证。
- **自研代码尚无。** `ws/src/ai`、`ws/src/ros`、`ws/src/simulation` 只有职责说明。

## 推进顺序

每一步都在上一步可运行的基础上增加一层，避免同时引入 ROS、控制与真机三类不确定性。

1. **平台基线**（完成）。上游闭环跑通，资产持久缓存，平台说明与操作手册就绪。
2. **评估与失败分类。** 可过夜无人值守的批量评估与汇总，成功率附置信区间；把失败分成抓取掉落、未抬起、放置失败等类型，并区分策略问题与仿真接触问题。后续每一项改动都以它为对照。
3. **接口契约。** 先写文档再写代码。第一个接口是 VLA 模块的输出：手腕目标位姿、行走指令与身体高度；写清单位与坐标系、频率与动作块、时间戳与 `use_sim_time`、超时，以及"进入安全状态"的入口。同时确定 ROS 话题的 QoS 与传输方式：当前全部走 UDPv4，传图像等大数据时先用 `ros2 topic hz` / `bw` 测量，再考虑共享内存或同进程组合节点。
4. **第一块砖**（待选，可以组合）：
   - **A. VLA 输出手腕位姿，中间加确定性层。** 用平台已有的手腕位姿逆运动学接口和数据集中的手腕位姿动作，改模态配置并在云端重新微调一次；VLA 不再直接给关节目标，审计与否决放在中间层。对应 [开发边界](PROJECT_GOALS.md#开发边界) 第 2 条。
   - **B. 安全审计层。** 每个控制步用捕获点估计稳定裕度，中途施加推力，主要指标是摔倒前的预警时间与误报率；裕度过低时替换 GR00T 的行走指令。完整的四天方案见 [Demo 方案](DEMO_PLAN.md)。监测部分可直接复用到 A。
   - **C. 控制回路不等 AI。** 按实测延迟让推理与执行并行，比较同步、朴素异步、块间平滑与实时分块等动作块调度方式。
5. **ROS 2 化。** 先做旁路观察：Isaac 的 ROS 2 bridge 发布 `/clock`、`/joint_states`、`/tf`、头部相机与审计量，`dev` 中用 RViz 查看、用 rosbag 记录到 `/runs`，不改变回路时序。再让 ROS 进入回路：VLA 作为节点，引入真实的异步与延迟，与第 2 步的指标对比。强化学习训练的内层循环始终不经过 ROS。
6. **模块化架构。** 部件注册动作集、中央调度器、稳定守护进程与前馈通道、分层安全，设想见 [项目目标](PROJECT_GOALS.md#模块化实现设想)。
7. **真机与控制核心。** 控制核心是不依赖 ROS、Isaac 与模型 SDK 的 C++ 库，以动态库形式由 sim 进程直接加载、由 ROS 节点与真机进程链接。G1 的底层接口是 `unitree_sdk2`（基于 Cyclone DDS 的 `LowCmd` / `LowState`）或 `unitree_ros2`（要求 `rmw_cyclonedds_cpp`，届时 `dev` 加装）；开发版机载计算单元为 aarch64 的 Jetson Orin（接入前核实型号），相关镜像需要多架构构建。

需要云端算力的步骤（4A 的微调、大规模数据生成）使用已发布的镜像在云端 GPU 上运行，评估端用 `--remote_host` 连接远程推理服务。

## 开发中的理论缺口

开发中遇到的理论问题在控制理论学习线里展开，学习由项目驱动：

| 缺口 | 在哪一步遇到 |
|---|---|
| 小样本成功率的置信区间与比较检验 | 2 |
| 带时延的采样控制；实时调度中的延迟与抖动；ROS 2 执行器与 QoS | 3、5、6 |
| 逆运动学；带任务优先级的全身控制（二次规划） | 4A、6 |
| 倒立摆模型、支撑多边形、ZMP、捕获点 | 4B、6 |
| flow matching 的采样与引导 | 4C |
| 前馈与反馈补偿、质心动力学、基于简化模型的 MPC | 6 |
| 行为树与任务调度；分层控制中的反射与规划 | 6 |
| 持续学习与灾难性遗忘 | 后期 |

## 已定的长期决定

| 日期 | 决定 |
|---|---|
| 2026-10-11 | 全部框架在容器中运行；镜像为 `dev`、`sim`、`policy` 三个，主机原生框架不参与项目 |
| 2026-10-11 | `src/` 只放项目开发源码，每个子目录是独立模块；`cppsrc/`、`pythonsrc/`、`rossrc/` 是顶层学习沙盒 |
| 2026-10-11 | Python 包只通过 Dockerfile 与锁文件进入镜像；新增依赖先讨论安装方式，不在终端 `pip install` |
| 2026-10-11 | 控制核心推迟到真机阶段，以动态库形式供其他层调用；此前不保留 `src/control` 占位 |
| 2026-10-11 | 测试与 CI 在全栈打通后再配置 |
| 2026-10-11 | `sim`、`policy` 使用 `ipc: host`，满足 dataloader 与分布式训练的共享内存需求 |
| 2026-10-18 | 仓库分两层：根目录放 Git、编排与基础设施，只在主机使用；开发工作区在 `ws/`，每个容器只挂载自己的目录，协作交给编排器；Git 只在主机上操作 |
| 2026-10-18 | 容器也服务于个人技术栈，允许冗余：`dev` 预装 ros2_control、MuJoCo（含 mujoco_ros2_control）、MoveIt 2 与 Nav2 核心，项目回路暂不使用；仿真方向只用 Isaac Sim 与 MuJoCo，不用 Gazebo；Open-RMF 等到涉及多机器人时再评估 |
| 2026-10-19 | 长期方向：机器人在真实环境中持续学习；AI 只负责决策与编排，不进入控制管线；决策经过审议，物理安全由确定性的门阀、审计与控制核心保证。详见 [项目目标](PROJECT_GOALS.md) |
| 2026-10-31 | 上游 G1 demo 定位为实验平台：平台说明集中在 `docs/platform/`，项目文档以目标、架构与开发为主，早期的学习计划与入门材料删除 |
| 2026-10-31 | 开发边界：VLA 当作现成部件，只关注接口；VLA 不直接控制电机 |
| 2026-10-31 | 长期软件形态：可热插拔的模块化架构（部件注册、中央调度器、稳定守护进程、分层安全） |
| 2026-10-31 | `sim` 容器的 `TMPDIR` 指向 `/data/assets/downloads`，场景资产持久缓存，启动从 15–30 分钟降到约 40 秒 |

## 暂缓的工程项

- 测试与 CI：全栈打通后，按模块分别建立 `sim` / `policy` 内的 pytest、`dev` 内的 `colcon test`、控制核心的 CTest。
- 在共享网络上限制 ROS 发现范围（Jazzy 的 `ROS_AUTOMATIC_DISCOVERY_RANGE=LOCALHOST`），需在第 5 步复测 `sim` ↔ `dev` 桥接后再设为默认。
- 失效处理的完整设计：接口里先预留"进入安全状态"，完整方案在模块化阶段设计。
